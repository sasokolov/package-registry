# Runbook'и

Каждый раздел — один сценарий дежурства: симптом, что происходит на самом
деле, что делать. Все команды предполагают `-config /etc/registry/config.yaml`
(в поде — `kubectl exec deploy/registry-registry -- ...`).

## Общее

Быстрый осмотр:

```bash
registry repl status      # сайт, головы журналов, курсоры, пины, parked, конфликты
registry repl peers       # мешевые связи и их состояние
registry config check     # конфиг валиден? (перед SIGHUP и в CI)
```

Заголовки ответов говорят, откуда пришли байты: `X-Registry-Source`
(`cache|upstream|stale|local|peer`) и `X-Registry-Site` (какой гео-сайт
ответил).

## Конфликт публикации между сайтами (правило K1)

**Симптом.** Алерт `RegistryPublishConflict`; клиенты получают `409` и
заголовок `X-Registry-Conflict` на конкретной координате.

**Что произошло.** Два сайта опубликовали *разные байты* по одной
координате (обычно во время партиции, на фиде с `publish_policy: local`).
Ядро не подменяет байты молча: канон выбран детерминированно (наименьший
sha256 — свойство содержимого, не часов), координата поставлена в карантин,
обе стороны записаны.

**Действия.**

```bash
registry repl conflicts               # человекочитаемо
registry repl conflicts -json         # полные дайджесты для автоматики
```

Решите, какая сборка правильная. Обычно это видно по сайту-источнику и
времени: `canonical_site`/`other_site`. При сомнении вытащите оба блоба и
сравните содержимое (оба целы — ни один не удалён):

```bash
# на сайте, где лежит нужный блоб
wget -qO- http://127.0.0.1:8081/internal/replication/v1/blobs/sha256/<sha> \
  -H "Authorization: Bearer $(cat /etc/registry/peer-token)" | sha256sum
```

Зафиксируйте выбор — он реплицируется и снимает карантин везде:

```bash
registry repl resolve -feed <feed> -path <path> -keep <полный sha256>
```

**Профилактика.** Для фидов, где важна строгая иммутабельность, ставьте
`publish_policy: forward:<home-site>`: запись всегда идёт на один сайт, и
проверка иммутабельности (409) остаётся авторитетной.

## Долгий ресинк / сайт отстал

**Симптом.** `RegistryReplicationStalled` или растущий `registry_repl_lag`.

**Диагностика.**

```bash
registry repl status
```

- `LAST ERROR` пустой, `APPLIED` растёт → сайт просто догоняет, ждите.
- `LAST ERROR` про `unreachable` → сетевой разрыв, см. следующий раздел.
- `APPLIED` стоит, parked events растут → события не применяются:
  `registry repl retry-parked` покажет причины.

**Действия.**

```bash
registry repl retry-parked            # причины и повторная попытка
registry repl resync -peer <name>     # перечитать журнал пира с нуля
```

`resync` безопасен в любой момент: применение идемпотентно. Если курсор
ушёл за горизонт хранения журнала пира, тот ответит `410`, и сайт сам
подтянет snapshot.

**Блобы отстают от манифестов** (ненулевой `registry_repl_durable_lag`):

```bash
registry repl backfill                       # что не хватает
registry repl backfill -dry-run=false        # дотянуть с пиров
```

## Разрыв связи между сайтами

**Симптом.** `RegistryReplicationPeerUnreachable`; `repl status` показывает
`peer ... unreachable`.

**Что работает.** Всё локальное: чтение, publish на локально-домашние фиды,
выдача из кэша. Не работает: сходимость между сайтами и publish на фид,
чей home — недоступный сайт (такой запрос получает `503` с `Retry-After` и
заголовком `X-Registry-Home-Site`).

**Действия.**

1. Проверьте сеть до `replication.peers[].url` и что порт открыт (у
   репликации отдельный listener и отдельная NetworkPolicy).
2. Проверьте креды: mTLS-сертификаты не истекли, bearer-файл совпадает.
3. После восстановления сайты сходятся сами; ничего запускать не нужно.
   Курсоры догоняют, алерты гаснут.

**Если сайт не вернётся** (потерян ЦОД): уберите его из `replication.peers`
у остальных — набор пиров перечитывается на лету. Журнал остальных
перестанет ждать его подтверждений и начнёт чиститься по расписанию.

## Ввод и вывод сайта

**Ввод нового сайта.**

1. Поднимите его с собственными PostgreSQL и S3, `site.name` — новый и
   уникальный. Имя фиксируется в БД при первом старте: чужое имя с чужой
   БД процесс не запустит.
2. Пропишите его в `replication.peers` на остальных сайтах и наоборот.
3. Сайт сам сделает snapshot-бутстрап. До сходимости он отдаёт hosted-фиды
   через peer-fallback (`X-Registry-Source: peer`), так что клиентов можно
   пускать сразу.
4. Дотяните блобы, если фиды ленивые: `registry repl backfill -dry-run=false`.

**Восстановление сайта, потерявшего БД.**

Пересозданный с нуля сайт получает новый UUID, и пиры перестают с ним
реплицировать — намеренно: под знакомым именем может оказаться кто угодно.

1. Убедитесь, что это действительно тот же сайт (тот же деплой, те же
   креды, а не чужой хост, занявший имя).
2. На каждом пире снимите пин:

   ```bash
   registry repl trust-reset -peer <имя-восстановленного-сайта>
   ```

3. Дальше сайт сходится сам: snapshot-бутстрап, затем журнал. Ленивым
   фидам дотяните блобы: `registry repl backfill -dry-run=false`.

Если UUID сменился без вашего ведома — не сбрасывайте пин. Это ровно тот
случай, ради которого он существует.

**Вывод сайта.**

1. Уберите его из `peers` у остальных (hot-reload).
2. Уберите из ингресса/DNS.
3. Убедитесь, что ни один фид не указывает на него в `publish_policy:
   forward:<site>` — иначе publish на этот фид станет `503`.

## Ротация peer-кредов

**mTLS (продакшен).** Выпустите новый сертификат тем же CA, обновите
Secret. Смена `replication.auth.*` требует рестарта пода (процесс это
сообщает в логе). Rolling update без простоя: старый и новый сертификаты
валидны у одного CA, поэтому порядок обновления сайтов не важен.

**Bearer (dev).** Токен общий для меша: обновите файл на всех сайтах, потом
перезапустите. Пока файлы различаются, опросы получают `401` — это видно в
`repl status` как `invalid replication credential`.

Смена UUID сайта (пересоздание БД) выглядит для пиров как чужой сайт под
знакомым именем; они откажутся реплицировать. Это защита от подмены, а не
сбой. `registry repl status` показывает это отдельной строкой
`PEER IDENTITY MISMATCH`, см. следующий раздел.

## Не работает вход через провайдера

**Когда.** Кнопка «Sign in with …» ведёт на страницу ошибки провайдера, или
возвращается, но консоль говорит, что вход не завершён.

Сначала посмотреть, что сайт вообще предлагает:

```bash
curl -fsS "$REGISTRY/api/v1/auth/methods"
```

- Метода с нужным issuer'ом нет → он не в `auth.oidc_issuers`.
- Есть, но `"flow":"token"` → у issuer'а не задан `client_id`. Кнопки не
  будет: реестр не зарегистрирован клиентом, редиректить не от чьего имени.

Дальше — по симптому:

- **Провайдер ругается на redirect_uri.** У него должен быть зарегистрирован
  ровно `<external_url>/ui/oidc/callback`. Реестр берёт адрес из
  `site.external_url`, а если тот пуст — из origin запроса; за прокси это даёт
  внутренний адрес. Задать `site.external_url` — правильное лечение.
- **Провайдер ругается на client_id или на публичный клиент.** Клиент должен
  быть **public** с PKCE (S256). Если провайдер настаивает на секрете —
  `client_secret_env` с именем переменной, а сам секрет в окружение пода.
  Пустая переменная даёт явную ошибку с её именем в логе.
- **Возвращается «this tab did not start a sign-in».** Callback открыли
  напрямую или в другой вкладке: verifier лежит в `sessionStorage` той
  вкладки, которая начинала. Начать заново.
- **Возвращается «nonce mismatch» или 401 на обмене.** Смотреть аудит-лог
  реестра: `browser sign-in failed` пишет причину, которую назвал провайдер.
  Ни кода, ни verifier'а, ни токена там нет и быть не должно.
- **Вход проходит, но прав нет.** Это уже вопрос доступа, а не входа:
  идентичность будет `oidc:<sub>`, дальше — следующий раздел и
  `access/explain`.

Разовая проверка, что реестр вообще видит провайдера (не завершает вход, но
показывает, дошло ли до discovery):

```bash
curl -sS "$REGISTRY/api/v1/auth/oidc/authorize?issuer=<issuer>&state=x&nonce=y&code_challenge=z"
```

502 здесь — недоступный или неправильно опубликованный провайдер; 401 —
issuer, которого нет в конфигурации.

## «Мне отказали, а не должны были»

**Когда.** CI-джоба или разработчик получает 403 там, где ожидает доступ, —
или, что хуже замечается, продолжает получать 200 там, где доступ должны были
закрыть.

Не гадать и не расширять политику «на всякий случай»: спросить у движка,
который и принял решение.

```bash
curl -fsS -H "Authorization: Bearer $ADMIN_TOKEN" \
  "$REGISTRY/api/v1/access/explain?path=feed/releases/maven:com.acme:lib@1.0.0&capability=publish&kind=oidc&project_path=acme/widget&ref=main"
```

Ответ называет решившее правило (`rule`), политику (`policy`), эффективные
capabilities и полный список привязанных политик. То же самое — форма
«Would this be allowed?» на странице **Access** в консоли.

Как читать ответ:

- `bindings` пустой — идентичность не выбрала ни одной привязки. Чинить
  привязку (`match`), а не политику: скорее всего не совпал `issuer`,
  `project_path` или `ref`. Если привязки есть, а `policies` не те — смотреть,
  какая именно привязка сработала: она названа в `bindings`.
- `rule` — это `deny` — запрет осознанный. Исключение делается **более
  специфичным** правилом, а не удалением запрета: точный путь бьёт `*`,
  меньше `+` — специфичнее, длиннее литеральный префикс — специфичнее.
- `rule` пустой, `allowed: false` — путь не покрыт ни одним правилом. По
  умолчанию отказ; нужен grant.
- Решает не та политика, что ожидалась — две политики встретились на одном
  уровне специфичности, и `deny` выиграл. Смотреть `policies` целиком.

Координату для `path` не надо собирать вручную: она в аудит-логе того самого
отказа, в том же виде.

**Проверить, что почините именно то.** Сначала спросить explain про
идентичность, потом менять политику, потом спросить снова. В Terraform это
`check`-блок с `registry_access_explain` — и проверять обе стороны: что нужное
разрешено и что ненужное всё ещё запрещено.

## Снять пакет с раздачи (карантин)

**Когда.** Юридическое требование, скомпрометированный релиз, ошибочная
публикация — всё, что нужно заблокировать быстрее, чем удалять.

```bash
registry repl quarantine -feed <feed> -coordinate 'maven:com.example:lib@1.0.0' \
  -reason manual -detail 'legal takedown #123'
```

Решение реплицируется: в пределах лага пира координата отдаёт `409` на всех
сайтах. Байты не удаляются — блокируется выдача (удаление блобов — отдельная
операция, `registry gc`, и только после того, как манифесты убраны).

Снять:

```bash
registry repl release -feed <feed> -coordinate '<coordinate>' -reason manual
```

Причины независимы: снятие `manual` не снимет `policy_osv` или
`cross_site_conflict`. Карантин конфликта снимается только через
`repl resolve` — он выводится из множества нерешённых конфликтов координаты.

## Припаркованные события

**Симптом.** Алерт `RegistryReplicationParkedEvents`; в `repl status`
ненулевой счётчик.

**Что это.** События, которые сайт пока не может применить: неизвестный тип
(пир новее), не доехавший блоб, часы уехали дальше `max_clock_skew`. Поток
за ними НЕ блокируется — они откладываются и переигрываются.

```bash
registry repl retry-parked    # покажет причины и попробует применить снова
```

Если счётчик не падает: неизвестный тип события означает, что этот сайт
старее пиров — обновите бинарь. Недоехавший блоб — `repl backfill`. Часы —
проверьте NTP.

## NTP и окно отзыва токена

**NTP обязателен.** События из будущего дальше `replication.max_clock_skew`
(по умолчанию 5 минут) паркуются, а не применяются. Разъехавшиеся часы —
самая частая причина растущих parked events.

**Окно отзыва токена.** После `registry token revoke -name <name>` токен
перестаёт работать:

```
на своём сайте:   не более auth.revocation_sweep            (по умолчанию 5s)
на других сайтах: pull_interval + время применения + auth.revocation_sweep
                  (типично 10–20s при pull_interval=10s)
```

Кэш проверенных токенов существует, чтобы чтение переживало падение
PostgreSQL (инвариант 7); поэтому отзыв бьёт не мгновенно, а в пределах
окна выше. Если нужно немедленно и везде — перезапустите поды (кэш живёт
только в памяти) после отзыва.

**Если PostgreSQL сайта недоступен**, отзыв на этом сайте не применяется
вовсе: sweeper не может прочитать таблицу, а уже проверенные личности
продолжают работать в пределах `auth.stale_identity_window` (по умолчанию
6h; `0` — отключить и деградировать громко). Это осознанный размен
доступности чтения на задержку отзыва. Для отзыва в такой ситуации:
перезапустите поды сайта (кэш в памяти) либо, если политика требует
жёсткости, поставьте `auth.stale_identity_window: 0` и примите, что падение
БД дольше `token_cache_ttl` останавливает аутентифицированное чтение.

## «Сколько это всё занимает и кто это качает»

**Когда.** Растёт счёт за хранилище; надо понять, какой фид его ест и можно ли
что-то выкинуть.

Страница **Usage** в консоли или:

```bash
curl -fsS -H "Authorization: Bearer $TOKEN" "$REGISTRY/api/v1/usage" | jq '
  .totals,
  (.feeds | sort_by(-.bytes) | .[:10] | .[] |
    {feed, kind, packages, bytes, downloads, bytes_saved, hit_ratio})'
```

Как читать:

- `totals.bytes` — то, что реально лежит в хранилище: каждый блоб один раз.
  Сумма по фидам всегда больше, потому что общий блоб посчитан у каждого
  владельца. Разница видна как `shared_bytes`.
- Прокси-фид с большими `bytes` и маленькими `downloads` — кандидат на
  удаление или на более агрессивный GC. `bytes - shared_bytes` — сколько
  освободится, если удалить фид целиком.
- `bytes_saved` = отдано минус вытянуто из апстрима. Ради этого числа кэш и
  существует; если оно около нуля на живом фиде — кэш не работает (короткий
  TTL, уникальные координаты, клиенты мимо кэша).
- `last_download_at: never` при непустом хранилище — фид не используется
  вообще.

**Освободить место:**

```bash
registry gc                 # dry run: что не нужно ни одному манифесту
registry gc -delete=true    # собрать
```

GC удаляет блобы, на которые не указывает ни один манифест. Чтобы кэш фида
действительно уменьшился, сначала должны исчезнуть манифесты — то есть фид
надо убрать из конфигурации (или дождаться, пока кэш протухнет по своей
логике). Просто запустить GC при живом фиде — ничего не собрать.

**Цифры устарели или нулевые.**

- `scan_enabled: false` — обход выключен (`server.usage_scan`). Скачивания
  всё равно считаются; хранилище будет неизвестно.
- `scanned_at` старее интервала — смотреть
  `registry_usage_scan_failures_total` и лог: обход мог не дотянуться до
  стораджа. Скачивания при этом свежие: их считают отдельно.
- Все скачивания нулевые после рестарта — счётчики копятся в памяти и
  флашатся раз в `server.usage_flush`; подождите интервал. Если
  `registry_usage_flush_failures_total` растёт — недоступна БД, дельты
  копятся и повторятся.

**Что из этого фида вообще нужно.**

```bash
curl -fsS -H "Authorization: Bearer $TOKEN" \
  "$REGISTRY/api/v1/usage/packages?feed=<feed>&limit=50" | jq -r \
  '.packages[] | "\(.downloads)\t\(.coordinate)"'
```

Только артефакты: метаданные тянутся при каждом резолве и в списке не
участвуют. Для прокси это заодно ответ на «что должно попасть в зеркало, если
апстрим исчезнет». Хвост подрезается на обходе инвентаря (тысяча на фид плюс
активные за 30 дней), так что список — про популярность, а не про историю.

**У прокси `packages` меньше, чем ожидается.** Координата пишется в манифест
при инжесте; артефакты, закэшированные более старой версией реестра, считаются
в файлах и байтах, но не в пакетах. Число сходится по мере обновления кэша.

## Сборка мусора в блоб-хранилище

```bash
registry gc                                   # dry-run, ничего не удаляет
registry gc -delete -min-age 168h             # удалить несвязанные блобы
```

GC держит advisory-lock на весь прогон (две реплики не сметут параллельно) и
никогда не трогает блобы младше `-min-age`. В гео-сетапе держите `-min-age`
заведомо больше максимального лага репликации: блоб, на который ещё не
пришёл манифест с другого сайта, локально выглядит несвязанным.
