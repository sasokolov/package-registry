# ADR: гео-репликация кластеров (мастер-мастер, «журнальная федерация»)

Статус: **принято архитектурно** (по запросу пользователя, 2026-07-26);
реализация — Фаза 7 PLAN.md. Формулировки правок инвариантов — на
подтверждении у пользователя.

## Цель и честная формулировка «мастер-мастер»

Несколько гео-сайтов; каждый сайт — полный автономный кластер (N stateless
реплик registry + свой PostgreSQL + свой S3-совместимый сторадж). Все сайты
обслуживают локальные чтения **и** записи и сходятся асинхронно.

Честная формулировка: active-active по чтению — всегда и везде; по записи
каждый сайт принимает publish любого фида (свои фиды — локально, чужие —
прозрачным сервер-сайд форвардом на home-сайт); полностью асинхронный
multi-writer одного фида — осознанный opt-in per feed с детерминированной,
громкой, human-mediated разрешалкой конфликтов. Линеаризуемого 409 через
WAN-партицию не даёт никто в индустрии — мы его и не обещаем.

## Принятый дизайн

**Всё межсайтовое — события append-only журнала приложения.** Никакой
репликации на уровне стораджа или БД как механизма корректности.

- **Transactional outbox**: таблица `repl_journal` в PG каждого сайта;
  событие пишется в той же транзакции, что и порождающее действие
  (publish, revoke, карантин). Событийная модель v1: `manifest_put`,
  `blob_available`, `token_revoke`, `quarantine_set`, `quarantine_release`,
  `conflict_resolve`; `schema_version` в каждом событии; tombstone-типы
  зарезервированы.
- **Порядок seq == порядок коммитов**: seq выделяется внутри SQL-функции
  `repl_hlc_next()` под замком единственной строки `hlc_state` — читатель,
  пагинирующий журнал по курсору, физически не может потерять событие
  (закрывает классическую дыру outbox-пагинации по IDENTITY-колонке).
- **HLC** (hybrid logical clock) генерируется в PG — реплики остаются
  stateless (инвариант 3).
- **Pull-mesh**: каждый сайт периодически (и по push-хинту `nudge`)
  забирает журнал у peer'ов через аутентифицированный внутренний API
  `/internal/replication/v1/*` на **отдельном listener'е**; курсоры
  per (peer, origin); advance курсора в одной транзакции с apply.
- **Идемпотентный, порядконезависимый apply**: merge по классам данных;
  property-тест «любая перестановка/дубли событий → байт-идентичное
  состояние» — часть DoD фазы.
- **Бутстрап и ресинк — один код-путь**: snapshot (REPEATABLE READ) +
  вектор watermark'ов → авто-backfill блобов → `Hoster.Reindex`; курсор за
  горизонтом retention журнала → 410 → автоматический snapshot-ресинк.
- **Блобы** переносятся по digest (`GET /internal/replication/v1/blobs/sha256/<hex>`):
  ключ и есть чексумма, принимающий сайт хэширует поток и отбрасывает
  несовпадение — перенос самоверифицируем (инвариант 5). Range-докачка,
  multi-peer fallback, режимы `eager` (блоб до манифеста; durability
  watermark = честный RPO) и `lazy` per feed.
- **PG hosted_manifests — истина, S3-манифест — проекция** (обязательство
  записи проекции фиксируется projection-outbox'ом в той же транзакции +
  continuous repair): read-path продолжает жить при падении PG по проекции
  (инвариант 7).

## Классы данных

| Класс | Правило |
|---|---|
| Прокси-артефакты и `meta/` | **Сайт-локальные производные.** Не реплицируются: каждый сайт наполняет кэш от своего апстрима. Bucket-репликация поверх `meta/` запрещена (сбросит ModTime и сломает TTL/SWR). |
| Hosted-блобы | Реплицируются по sha256 (eager/lazy), перенос самоверифицируем. |
| Hosted-манифесты релизов | Реплицируются событиями `manifest_put`; конфликты — правило K1. |
| Индексы hosted-фидов (maven-metadata.xml, dist-tags, versions) | **Не реплицируются никогда** — пересобираются локально `Hoster.Reindex` из сошедшегося множества манифестов (Reindex — детерминированная чистая функция множества манифестов). |
| Статические токены | Создание — сайт-локально (репликация не создаёт полномочий); **отзыв** реплицируется по хэшу (sticky). Кросс-сайтовая идентичность — OIDC (stateless, работает на всех сайтах). |
| Карантин | Реплицируется (`quarantine_set`/`release`, ключ — `(feed, path)`). |
| Аудит | Сайт-локален (+ колонка `site`); агрегация — на уровне observability. |

## Как сделать удалённый сайт быстрым, не нарушая инвариант 15

Прокси-кэш не реплицируется — и не должен: это производные данные, у каждого
сайта свой апстрим и свой TTL. Но из этого не следует, что удалённый сайт
обязан ходить в интернет: **его апстримом может быть другой сайт**.

```yaml
# Сайт A — единственный с внешним каналом.
feeds:
  - name: central
    upstream: https://repo1.maven.org/maven2
    upstream_rps: 4

# Сайт B — кэширует через A.
feeds:
  - name: central
    upstream: http://registry-a:8080/maven/central
    upstream_rps: 50
```

Это обычное проксирование, не репликация: B промахивается — идёт к A, у A
попадание в кэш, B кладёт копию себе. Инвариант 15 цел, потому что через
границу сайта по-прежнему не едет ничего производного — B сам решил, что его
апстрим находится там.

Что это даёт (замерено на двух сайтах, сборка `stleary/JSON-java`, 1510
обращений к реестру):

| Прогон | Время | Откуда |
|---|---|---|
| A, холодный кэш (реальный Central) | 4 мин 20 с | 750 upstream |
| B, холодный кэш (апстрим — A) | 53 с | 753 upstream, **A в интернет не ходил ни разу** |
| B, тёплый кэш | 12 с | 1510 из 1510 — cache, A не потревожен |

Hosted-содержимое при этом не участвует в проксировании вообще: опубликованное
на A появляется на B фактом репликации. Первый запрос может ответить
`X-Registry-Source: peer` — манифест доехал, блоб ещё нет, — дальше `cache`.
Это ровно то окно, ради которого существует `peer_fallback`.

Ограничение топологии очевидное и его стоит проговорить: B зависит от
доступности A для промахов. Кольцо или mesh из proxy-апстримов делать не надо —
получится цикл; в цепочке должен быть ровно один сайт с внешним каналом (или
несколько независимых, каждый со своим).

## Модель записи: write-affinity по умолчанию

У каждого hosted-фида есть `home_site` (`publish_policy: forward:<site>`).
На чужом сайте publish **аутентифицируется локально** и реверс-проксируется
на home по репликационному каналу с on-behalf-of identity (audit на home
фиксирует реального публикатора). Никаких 307 наружу: реальные клиенты
(npm, maven) не переносят cross-host redirect с кредами. Home недоступен →
честный `503 + Retry-After` + машиночитаемый указатель home-URL — запись
выбирает консистентность, чтение — доступность. Локальная семантика
инварианта 4 не меняется: exists → 409, авторитетно на home.

`publish_policy: local` (симметричный multi-writer publish) — осознанный
opt-in per feed; тогда конкурентный конфликт разрешает правило K1.

## Правило K1 — детерминированное разрешение конфликта публикаций

Для множества событий `manifest_put` одной координаты `(feed, path)`:

1. Равный `sha256` → идемпотентность, конфликта нет.
2. Различные `sha256` → конфликт:
   - каноническое состояние = событие с **лексикографически наименьшим
     sha256** — min по множеству: коммутативно, ассоциативно, идемпотентно,
     не зависит от порядка доставки и от часов (подделка/отставание часов
     не даёт украсть координату);
   - координата немедленно карантинится: `GET → 409 + X-Registry-Conflict`,
     повторный publish → 409 — **на всех сайтах**; после детекции никто не
     отдаёт ни «победителя», ни «проигравшего» — молчаливой подмены байтов
     в системе не существует;
   - обе стороны — в `publish_conflicts` + audit + метрика + алерт; оба
     блоба сохраняются (content-addressed);
   - разрешение — только явное: `registry repl resolve --feed --path
     --keep <sha256>` порождает журналируемое `conflict_resolve`.
3. При дефолтной политике `forward:<home>` шаг 2 в нормальной работе
   недостижим; правило — всегда включённая страховка от split-brain и
   мисконфигурации home.

**Как это реализовано (уточнения по итогам Фазы 7).** Карантин конфликта —
не самостоятельная запись, а **производное** состояние: он активен ровно
пока у координаты есть незакрытые конфликты в `publish_conflicts`. Иначе
одна координата Maven (GAV покрывает jar, pom, sources) ловила бы разблокировку
от резолюции соседнего пути, а стамп детекции у каждого сайта свой.
Резолюция терминальна: она хранится в `conflict_resolutions` и консультируется
каждым последующим merge, поэтому поздний конфликтующий publish не переоткрывает
решённую координату — он лишь дописывается в набор увиденных дайджестов
(для аудита). Резолюция несёт размер и чексуммы выбранной стороны: без них
координата сохранялась бы нулевой длины при совпадающем sha256.

## Безопасность

- Internal API — только на отдельном listener'е (`replication.internal_listen`
  обязателен при включённой репликации), mTLS в prod; на публичный роутер
  не монтируется. NetworkPolicy в helm.
- **Репликация не создаёт полномочий**: в протоколе нет событий, создающих
  учётные данные или снимающих ограничения; только отзывы и контент,
  верифицируемый по хэшу. `token_upsert` не существует.
- Origin-pinning: applier принимает события только от аутентифицированного
  peer'а с совпадающим origin (mesh-only в v1, без relay); пара
  (site.name, UUID) пинится при handshake — фенсинг клонов site_id.
- Секреты — только file-ссылками (K8s Secrets), не inline в YAML
  (инварианты 8/12); peer-креды в логах — первые 8 символов хэша.
- Окно принятия отозванного статического токена = replication lag +
  `token_cache_ttl`; на изолированном сайте во время партиции — не
  ограничено (документируется; чувствительным фидам — OIDC).

## Партиция и heal

Чтение живо везде (кэш/апстрим/stale/peer-fallback под circuit breaker'ами).
Publish: локально-homed фиды работают; удалённо-homed → 503 с указателем;
`local`-фиды принимают с риском K1. Heal автоматичен: курсоры догоняют,
merge идемпотентен; digest множества манифестов per feed в `/status`
подтверждает сходимость. Расхождение digest'ов дольше окна лага → алерт:
молчаливой дивергенции не существует ни в одном режиме.

## Read-path и лаг

На hosted-фидах (per-feed `peer_fallback: true`) miss манифеста **или**
блоба → sha-пинованный fetch у peer'ов, ответ несёт
`X-Registry-Source: peer`; все ответы несут `X-Registry-Site`. Лаг
репликации для читателя невидим. Negative-cache per replica (TTL ~30s).

## Наблюдаемость

`registry_repl_lag{peer,origin}` (head − applied + возраст последнего
успешного poll), durability watermark (RPO), конфликты, dead-letter,
parked, projection divergence, digest множества манифестов per feed.

## Отвергнутые альтернативы

- **Стораджевая репликация как механизм корректности** (MinIO site
  replication, S3 CRR): MinIO-only/one-cloud coupling (противоречит
  «стораджи — модули»), у MinIO site replication принудительная
  синхронизация IAM всей инсталляции, конфликт одноимённых ключей — тихий
  LWW без сигнала, лага без RTC никто не ограничивает, CRR не копирует
  существующие объекты (бутстрап всё равно app-level). Допустима позже
  только как необязательный ускоритель переноса блобов.
- **PG multi-master** (native bidirectional logical replication, pgEdge
  Spock, EDB PGD): не реплицируются sequences/DDL, конфликт стопит apply
  worker (native), операционная сложность несоразмерна маленькому,
  журналообразному состоянию. Все зрелые аналоги (GitLab Geo, Harbor,
  Pulp, Artifactory) держат PG сайт-локальным и синхронизируются
  app-журналом.
- **Federation/on-demand без журнала**: анти-энтропия по digest'ам без
  журнала даёт steady-state дыру «манифест есть/блоба нет», O(N²) LIST-ы,
  вероятностный инвариант 4.
- Prior art: Artifactory Federated Repositories (единственный «мастер-
  мастер» на рынке) разрешает конкурентные публикации **молчаливым LWW по
  часам** — ровно то, что наш инвариант 4 запрещает; поэтому K1 —
  контентно-детерминированный и громкий.

## Эскиз конфигурации

```yaml
site:
  name: eu-1
  external_url: https://eu-1.registry.example.com

replication:
  enabled: true
  internal_listen: ":8081"      # отдельный listener, обязателен
  auth:
    type: mtls                  # mtls (prod) | bearer (dev); секреты — file-ссылки
    ca_file: /var/run/secrets/repl/ca.crt
    cert_file: /var/run/secrets/repl/tls.crt
    key_file: /var/run/secrets/repl/tls.key
  topology: mesh                # v1: только mesh
  peers:
    - name: us-1
      url: https://repl.us-1.registry.example.com:8081
      pull_interval: 10s
  nudge: true
  journal_retention: 720h
  max_clock_skew: 5m
  blob_fetch: {concurrency: 4, resume: true}

feeds:
  - name: internal-maven        # дефолтная модель записи
    format: maven
    hosted: true
    publish_policy: forward:eu-1
    replication_mode: eager
    peer_fallback: true
  - name: sandbox-npm           # осознанный opt-in active-active
    format: npm
    hosted: true
    publish_policy: local
    replication_mode: lazy
    peer_fallback: true
  - name: maven-central         # прокси-фиды в федерации не участвуют
    format: maven
    upstream: https://repo1.maven.org/maven2
```

## Что уточнилось при реализации

- **Идентичность сайта durable.** UUID пира пиннится в БД
  (`repl_peer_identity`), а не в памяти процесса: иначе каждая реплика и
  каждый рестарт решали бы заново, кто такой пир (инвариант 3). Курсор
  дополнительно помнит инкарнацию origin'а, поэтому пересозданный сайт
  (журнал с единицы) детектируется, как бы быстро он ни публиковал.
  Возврат такого сайта — явное решение оператора: `repl trust-reset`.
- **Retention журнала — самостоятельный пол.** Обрезка до подтверждённого
  всеми пирами водяного знака безопасна, но недостижимый или удалённый пир
  иначе держал бы журнал вечно; по истечении `journal_retention` записи
  удаляются, а отставший пир переезжает на snapshot через 410.
- **Snapshot несёт факты целиком.** Манифесты, незакрытые конфликты,
  операторские резолюции (с размером и чексуммами), активные карантины и
  хэши отозванных токенов. Оба пути сходимости — журнал и snapshot —
  сверяются тестом на идентичность результата.
- **Mesh-only origin pinning.** Сайт принимает от пира только его
  собственный журнал; чужие потоки приходят первыми руками от их источника,
  где их можно аутентифицировать.
- **Отзыв токена при недоступной БД.** Проверенные личности переживают
  падение PostgreSQL в пределах `auth.stale_identity_window` (по умолчанию
  6h, `0` отключает) — размен доступности чтения на задержку отзыва,
  зафиксированный в docs/runbooks.md.

## Открытые вопросы (решает пользователь)

1. Сколько сайтов и где home каких фидов; нужен ли `publish_policy: local`
   в v1 или достаточно forward-only (K1 остаётся страховкой) — режет объём.
2. UX конфликта K1: 409 всем до `repl resolve` (принятый дефолт) или
   отдавать канонический sha256 с предупреждающим заголовком.
3. Гео = ещё и DR (тогда `eager` по умолчанию + алерты на RPO) или только
   локальность чтений (`lazy` дешевле по WAN).
4. Токены: подтвердить модель «создание сайт-локально, кросс-сайт — OIDC».
5. Допустимо ли окно отзыва токена lag+TTL (партиция — не ограничено).
6. Один geo-DNS hostname или per-site URL (принятый дизайн безопасен для
   per-site, т.к. meta/ не реплицируется).
7. Гомогенны ли стораджи (можно ли mc mirror как ускоритель бутстрапа).
8. Место Фазы 7: после Фазы 5 (рекомендация) или сразу после Фазы 3.
   *(Решено: реализована после Фазы 6.)*
9. Нужен ли user-facing delete/takedown (tombstone-события зарезервированы).
